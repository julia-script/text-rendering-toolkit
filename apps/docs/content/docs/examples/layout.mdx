This example fetches three font files in the application, gives their bytes to `loadFont()`, prepares
the editable string, and supplies the resulting font registry to `layoutPreparedText()`.

Nothing in this path imports Three.js or checks for WebGPU. Change the text, width, line height, or alignment and
watch the line boxes, baselines, lazily requested outlines, ordered COLR v0 layers, scripts,
directions, fallback font keys, and coordinates update from the same public data a renderer would
receive. The explicit line-height control keeps mixed-font baseline steps uniform. Toggle any visual
layer independently; the subtle maximum-width ruler shows the wrapping constraint, while the metric
cards report block and line dimensions, baselines, and break kinds.

The decoration controls call `deriveTextDecorations()` after layout and draw its analytic segments
directly as SVG. Switch between solid, dotted, and wavy underline or solid strikethrough, choose a
color independent from the glyph fill, compare automatic font metrics with numeric thickness and
offset, and toggle exact ink skipping. Automatic placement is chosen once for the complete decoration
span, so Arabic and emoji fallback cannot make one underline jump. The SVG renderer then uses the
outlines it already owns to cut small gaps around actual descenders and color-emoji layers. None of
those appearance changes prepares or shapes the text again, and the example has no Three.js dependency.

Try a narrow width with punctuation, Arabic text, or another supported emoji. Preparation remains
font-neutral, while the later font-aware stage greedily selects the last exactly measured Unicode
opportunity that fits and reshapes each accepted line fragment independently.
